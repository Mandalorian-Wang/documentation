This page explains how roadmap planning should be communicated in BoxLite docs without turning planning notes into release promises.

## Planning Standard

Use this page only for:

- planning themes that maintainers have explicitly decided to share,
- links to active GitHub issues or discussions,
- areas where contributor help is useful,
- status labels that are clearly non-release commitments.

Do not use this page for:

- exact release dates unless maintainers have already published them elsewhere,
- placeholder versions such as `v1.x`,
- speculative feature lists without a linked source of truth,
- statements that imply a capability is shipping when it is only being discussed.

## Status Labels

If you publish roadmap items here, use labels that describe planning confidence instead of release certainty:

- `Exploring` for areas under investigation
- `Planned` for work maintainers intend to schedule
- `In progress` for work already underway
- `Released` only after the change appears in [Release Notes](/community/release-notes) or GitHub Releases

## What To Link

Each roadmap item should link to one or more BoxLite source artifacts:

- a GitHub issue,
- a GitHub discussion,
- a pull request,
- a design note maintained in this docs set.

## How Release Notes And Roadmap Differ

Use the two pages for different jobs:

- [Release Notes](/community/release-notes) record what has been published.
- This roadmap page should describe what maintainers are intentionally discussing or preparing.

## How To Request Roadmap Changes

We prioritize roadmap additions based on:

- evidence from BoxLite users and contributors,
- fit with BoxLite's actual product direction,
- implementation feasibility,
- maintainer capacity.

### How to Request a Feature

1. **GitHub Issues** - Open a feature request issue
2. **GitHub Discussions** - Post in the Ideas category
3. **Discord** - Share in the #feature-requests channel

### What to Include

When requesting a feature, please include:

- Use case - What problem are you solving?
- Expected behavior - How should it work?
- Alternative solutions - What have you tried?
- Priority - How important is this to you?

## Contributing to Roadmap

The roadmap is developed based on:

1. **Community feedback** - Your feature requests and use cases
2. **Customer input** - Enterprise requirements
3. **Technical strategy** - Long-term architectural decisions

To contribute to the roadmap:

- [Contribute code](/community/contributing) - Implement features
- [Write documentation](/community/contributing) - Improve docs
- [Share feedback](https://github.com/boxlite-ai/boxlite/discussions) - Help us prioritize

## Publishing Guidance

Before adding roadmap content, confirm that it meets all of these checks:

1. The item points to a BoxLite source artifact.
2. The wording does not imply a release date unless one has already been publicly published.
3. The item is described as planning, not as shipped functionality.
4. Any shipped result is documented in [Release Notes](/community/release-notes).
