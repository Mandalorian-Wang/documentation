This tutorial explains the core pattern for connecting an LLM to BoxLite. It is intentionally framework-agnostic.

Use this page to understand the execution loop, state model, and design decisions. Use the pages in [AI Integrations](/integrations/overview) when you need runnable code for a specific provider or agent framework.

## What this tutorial is for

This tutorial is the right starting point if you want to:

- let an LLM request code execution inside a sandbox,
- understand how tool calling maps onto BoxLite,
- decide when to reuse a box and when to start a new one,
- separate the BoxLite execution layer from the LLM orchestration layer.

This tutorial is not the right place to learn provider-specific SDK details. Those belong in [AI Integrations](/integrations/overview).

## The core execution loop

The pattern is the same regardless of which model provider or agent framework you use:

1. Define a tool contract such as `execute_python(code)`.
2. Send the user request to the LLM with that tool available.
3. When the model asks to call the tool, run the requested work inside BoxLite.
4. Return the execution result to the LLM as a tool result.
5. Repeat until the model returns a final answer instead of another tool call.

BoxLite owns the isolated execution environment. Your LLM framework owns the conversation, tool routing, retries, and final response generation.

## What BoxLite should and should not do

BoxLite should be responsible for:

- sandbox startup and teardown,
- command or code execution,
- filesystem state inside the sandbox,
- runtime isolation from the host.

BoxLite should not be responsible for:

- prompt orchestration,
- agent memory,
- conversation history,
- provider-specific tool schemas,
- model selection or routing.

Keeping that boundary clean prevents the docs from mixing platform behavior with framework behavior.

## Choosing the right box type

For most LLM tool-calling workflows, start with [CodeBox](/reference/python/box-types#codebox).

Use [SimpleBox](/reference/python/box-types#simplebox) when the model should run shell commands or scripts you orchestrate outside the `CodeBox` abstraction. Use [BrowserBox](/reference/python/box-types#browserbox) or [ComputerBox](/reference/python/box-types#computerbox) when the tool needs a browser or desktop instead of plain code execution.

## State model: what persists and what does not

This is the most important BoxLite-specific concept for LLM integrations:

- Files written inside the same box persist until you stop or remove that box.
- Packages installed into the same box persist for later tool calls in that same box.
- A single `run()` or `exec()` call is still a separate process.
- In-memory variables and Python function definitions do not carry from one execution call to the next unless your application stores them externally and replays them.

That means one box can behave like a persistent workspace, but not like a long-lived Python interpreter unless you explicitly build around that model.

## Reuse one box or create many

Use one box per conversation when:

- later tool calls need files from earlier steps,
- package installation cost matters,
- the user experience depends on continuity inside one workspace.

Use one box per task or per request when:

- you need hard separation between jobs,
- you do not want state carryover,
- cleanup simplicity matters more than warm-state reuse.

If you are designing for concurrency, timeouts, isolation policy, or resource sizing, continue to [AI Agent Production Patterns](/guides/ai-agent-integration).

## Minimal implementation checklist

Before you wire BoxLite into any LLM framework, confirm these decisions:

1. What tool contract will the model see?
2. Which BoxLite box type matches that tool?
3. Will one box be reused across multiple tool calls?
4. What state should persist between calls?
5. What should happen when code execution fails or times out?
6. Which framework will own retries and message history?

If those decisions are unclear, provider-specific code will only hide the architecture problem instead of solving it.
