---
title: "Audit Logging"
description: "Guidance for logging security-relevant activity around BoxLite deployments without assuming a built-in enterprise audit subsystem."
---

BoxLite is an open source runtime, not a hosted security platform. Treat audit logging as an operational responsibility in the layers around BoxLite:

- your application API
- your job orchestration layer
- your BoxRun deployment, if you use BoxRun
- your host and infrastructure logs

This page explains what you should log and how to think about retention and correlation. It does **not** claim that BoxLite exposes a built-in enterprise audit log API or a fixed event schema.

## What to Log

If you are running BoxLite in production, the minimum useful security trail usually includes:

- who requested sandbox creation
- which image or template was used
- when command execution started and ended
- whether networking was enabled
- whether ports or host mounts were exposed
- whether a box was stopped, deleted, or left persistent
- what application-level identity initiated the action

These events are most reliable when logged by the service that calls BoxLite, not by assuming the runtime itself will emit a complete audit stream.

## Recommended Event Categories

### 1. Box Lifecycle

Log at least:

- box created
- box started
- box stopped
- box deleted
- template or image selected

### 2. Execution Activity

Log at least:

- command requested
- execution completed
- exit code
- timeout or forced termination

Do **not** log raw command output by default if it may contain secrets or user data.

### 3. Security-Relevant Configuration

Log changes or decisions around:

- security preset selection
- network enabled vs disabled
- port forwarding configuration
- host mounts or persistent disk usage
- image source changes

### 4. Administrative Actions

If you expose BoxLite through an API or management layer, log:

- token or credential changes in your own system
- permission changes
- operator-initiated deletes or cleanup jobs
- configuration reloads and deployment changes

## Example Application-Level Log Shape

The exact format is up to your system, but a structured JSON event like this is usually enough:

```json
{
  "timestamp": "2026-04-19T10:30:45Z",
  "event": "box.exec.completed",
  "actor_id": "user-123",
  "request_id": "req-abc",
  "box_id": "box-001",
  "image": "python:3.11-slim",
  "network_enabled": false,
  "exit_code": 0
}
```

The important property is correlation, not a specific vendor schema.

## Correlation Strategy

Make it possible to connect:

- the external request
- the internal job or workflow
- the box identifier
- the execution result

In practice, that means carrying a request or correlation ID from your frontend or API layer into the system that invokes BoxLite.

## Retention Guidance

Retention depends on your own legal and operational requirements. This documentation does not prescribe compliance-specific retention periods.

As a practical starting point:

- keep recent operational logs online for debugging
- archive longer-lived security records if your organization requires it
- separate high-volume execution telemetry from security-significant events

## SIEM and Centralization

If your organization uses a SIEM, forward your **application and infrastructure logs** there. BoxLite can participate in that workflow through the logs emitted by the systems around it, but this page does not assume a built-in BoxLite-to-SIEM integration layer.

## Common Mistakes

- assuming BoxLite automatically provides a complete enterprise audit trail
- logging full stdout or stderr for workloads that may handle secrets
- keeping no correlation ID between API requests and box activity
- treating infrastructure logs as a substitute for application-level audit records
