Use this page as the entry point for BoxLite security documentation.

This section is not the place for low-level isolation internals. If you want to understand the defense-in-depth stack, jailer boundary, platform-specific sandboxing, or hypervisor-layer isolation, use [Architecture: Security & Isolation](/architecture/security).

The purpose of this section is different:

- define the security boundary between BoxLite and the user
- explain which operational controls matter in real deployments
- route you to the right page for secrets, auditability, hardening, and policy

## Start Here

Most teams evaluating BoxLite security need answers to four practical questions:

1. What does BoxLite protect by default?
2. What am I still responsible for?
3. How should I handle secrets and logs in production?
4. Where should I look when I need hardening guidance instead of architecture internals?

This section is organized around those questions.

## What BoxLite Owns vs What You Own

Start with [Shared Responsibility Model](/security/shared-responsibility).

That page is the most important security page in the product docs because it explains the boundary clearly:

- BoxLite owns the isolation mechanisms and enforcement primitives
- you own workload trust decisions, configuration choices, network exposure, credential handling, and deployment hygiene

If you skip that boundary, the rest of the section is easy to misread.

## Recommended Reading Order

For most engineering teams, the right order is:

1. [Shared Responsibility Model](/security/shared-responsibility)
2. [Secrets Management](/security/secrets-management)
3. [Audit Logging](/security/audit-logging)
4. [Threat Model and Hardening](/security/threat-model-and-hardening)
5. [Security Policy](/security/security-policy)

This sequence mirrors how security decisions usually happen in practice: first clarify ownership, then protect credentials, then make operations observable, then harden, and only then review policy-level commitments.
