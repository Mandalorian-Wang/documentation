description: "Guidance for handling secrets safely when using BoxLite, without assuming built-in secret manager integrations."

BoxLite should be treated as an execution boundary, not as your source of truth for secret storage.

This page focuses on safe usage patterns:

- avoid baking secrets into images, templates, or source code
- inject secrets only at the point of execution
- minimize where secrets appear in logs, files, and command lines

It does **not** assume built-in integrations with Vault, cloud secret managers, or a dedicated BoxLite secret abstraction unless those capabilities are documented and verified elsewhere.

## Core Rule

Store secrets outside BoxLite. Pass them into workloads only when needed.

In practice, that usually means:

- your application reads a secret from its own trusted source
- your application passes the secret into the workload at runtime
- the workload uses it and exits or drops it as soon as possible

## Safe Patterns

### Prefer Runtime Environment Injection

Use environment variables at execution time rather than hardcoding credentials:

```python
import os

result = await box.exec(
    "python",
    "app.py",
    env={
        "API_KEY": os.environ["API_KEY"],
    },
)
```

This is safer than embedding the secret in source code or writing it into an image layer.

### Avoid Command-Line Secrets

Do not pass credentials directly in shell arguments when you can avoid it:

```python
# Avoid this pattern when possible
await box.exec("python", "app.py", "--api-key", os.environ["API_KEY"])
```

Command-line arguments are easier to expose in logs, process listings, and debugging output.

### Avoid Long-Lived Secrets in Templates

Do not build templates that already contain:

- API keys
- private tokens
- database passwords
- long-lived certificates

Templates should capture environment shape, not durable credentials.

## Host Responsibility

Because BoxLite is an execution runtime, secret hygiene mostly lives in the host application and deployment environment.

Your responsibilities include:

- deciding where secrets are stored
- deciding who can retrieve them
- deciding when they rotate
- deciding which workloads receive them

BoxLite does not remove the need for standard secret management practices in your own system.

## Logging and Debugging Hygiene

Be careful when debugging workloads that receive secrets.

Avoid:

- printing secret-bearing environment variables
- logging full command invocations when they include sensitive values
- writing secret files into shared host mounts unless you fully control cleanup

Prefer:

- redacted application logs
- short-lived runtime injection
- explicit cleanup of temporary files created by your own application

## File-Based Secrets

If a workload must read a secret from a file, create that file at runtime and keep its lifetime short.

General pattern:

1. create a temporary file
2. write the secret
3. use it
4. delete it as soon as the workload no longer needs it

Do this in your own application layer rather than assuming BoxLite provides a special secret-file facility.

## Rotation Guidance

Secret rotation should happen in the system that owns the secret, not inside BoxLite.

Reasonable rotation model:

- rotate in your secret store or deployment environment
- restart or re-run workloads with the new value
- avoid keeping long-lived boxes around with stale credentials if rotation is frequent

## Common Mistakes

- committing secrets into example code or templates
- treating BoxLite as a secret manager
- passing credentials in command-line flags by default
- leaving secret material in shared mounts or exported artifacts
- assuming automatic masking, rotation, or cloud secret-manager integration without verification
